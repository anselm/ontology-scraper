## 1. LLM knowledge-graph extraction (2024–2026)

**Microsoft GraphRAG** (Edge et al., arXiv 2404.16130) builds "an entity knowledge graph from the source documents" with an LLM, then community summaries (https://arxiv.org/abs/2404.16130). Its extraction findings matter for us: chunk size is "a fundamental design decision"; longer chunks "suffer from degraded recall of information that appears early in the chunk"; on HotPotQA "GPT-4 extracted almost twice as many entity references when the chunk size was 600 tokens than when it was 2400". Their fix is a capped self-reflection loop asking the model to "glean" missed entities. Entities and relationships come from one multipart prompt per chunk as delimited tuples; "claims" (dates, events) are a second prompt. Dedup is "exact string matching"; duplicate relationships become edge weights; they call the method "generally resilient to duplicate entities" only because later summarisation groups them (https://arxiv.org/html/2404.16130v2). For a canonical entity store that resilience does not apply.

**KGGen** (Mo et al., arXiv 2502.09956, NeurIPS 2025) is the clearest published two-pass design. Extraction: entities first, then "a second step outputs relations given the source text and entity list"; aggregation "does not require an LLM" and lowercases. Resolution: "semantic embeddings of every item using S-BERT and cluster using k-means into clusters of 128 items"; per item retrieve k=16 neighbours "using a fused BM25 and semantic embedding approach"; an LLM is asked to "identify exact duplicates from this set" and pick a canonical alias; repeat "until no items remain in the cluster". MINE-1: "KGGen scored 66.07% on average, significantly outperforming GraphRag 47.80% and OpenIE 29.84%" (extraction with Gemini 2.0 Flash). Admitted failures: "over or under de-duplication of entities and relations", corpora only to ~5M tokens, weak in medicine/finance (https://arxiv.org/html/2502.09956v2).

**iText2KG** (Lairgi et al., arXiv 2409.03284, WISE 2024): Document Distiller, Incremental Entity Extractor, Incremental Relation Extractor, Graph Integrator; motivated by the fact that "unresolved and semantically duplicated entities and relations still pose challenges" (https://arxiv.org/abs/2409.03284). Search summaries say it resolves by cosine similarity on embeddings; I did not verify that in the paper.

**LangChain LLMGraphTransformer**: `allowed_nodes`/`allowed_relationships` default empty, "allowing all node types"; `strict_mode` (default True) filters to the lists; it uses `with_structured_output` and falls back to a prompt path where properties "cannot be used in combination with a LLM that doesn't support native function calling" (https://github.com/langchain-ai/langchain-experimental/blob/main/libs/experimental/langchain_experimental/graph_transformers/llm.py). No resolution step. Neo4j's `SimpleKGPipeline` by default will "merge entities that have the same label and identical name property", offers RapidFuzz and spaCy resolvers, and warns of "the risk of incorrectly merging distinct entities" (https://graphacademy.neo4j.com/courses/genai-graphrag-python/4-customisation/4-resolving-entities/).

**Survey.** Bian (arXiv 2510.20345, Oct 2025): schema-driven extraction gets "high consistency but limited flexibility", "rigid ontological templates restricts scalability and cross-domain generalization"; schema-free "prioritizes coverage and discovery over structural regularity"; fusion means "entity alignment, disambiguation, deduplication, and conflict resolution" (https://arxiv.org/html/2510.20345v1). It does not quantify hallucinated triples; I found no paper that does for news.

**Small encoders.** GLiNER2 (Zaratiana et al., arXiv 2507.18546, EMNLP 2025 demo): 205M parameters, NER + classification + "hierarchical structured data extraction" from a declarative schema on CPU; 130–208 ms latency vs 358–463 ms for GPT-4o via API; zero-shot CrossNER F1 0.590 vs 0.599; classification 0.72 vs 0.84 (https://arxiv.org/html/2507.18546v1). The HF card adds relation extraction, unevaluated in the paper (https://huggingface.co/fastino/gliner2-large-v1). **NuExtract 2.0**: 2B/4B/8B Qwen-VL-based template extractors with types like `verbatim-string` ("present verbatim in the input"); 2B and 8B MIT, 4B Qwen Research License; 8B ExtractBench mean 49.42 (https://huggingface.co/numind/NuExtract-2.0-8B). **REBEL**: BART seq2seq, "more than 200 different relation types", code CC BY-SA-NC 4.0 (https://github.com/Babelscape/rebel). **spacy-llm**: NER/REL/sentiment/entity-linking tasks over OpenAI/Anthropic/HF, "still experimental", LLMs for prototyping and supervised models "for production" (https://github.com/explosion/spacy-llm). **Stanford OpenIE**: open-domain triples from entailed clause fragments; nominal mode "greatly overproduces such triples" (https://stanfordnlp.github.io/CoreNLP/openie.html).

**Structured output.** Instructor validates with Pydantic and retries on failure (`max_retries`), supports Ollama and Anthropic, has a TypeScript port (https://python.useinstructor.com/). Ollama enforces a JSON schema via `format`, recommends temperature 0 and repeating the schema in the prompt (https://docs.ollama.com/capabilities/structured-outputs). Anthropic uses constrained decoding via `output_config.format` and `strict: true` tools; no recursion, numeric/string constraints or `additionalProperties` other than false; first use compiles a grammar cached 24 h; the guarantee is structure, not content, and lapses under refusal or truncation (https://platform.claude.com/docs/en/docs/build-with-claude/structured-outputs).

**Does forcing JSON hurt?** Tam et al. (EMNLP 2024 Industry): "a significant decline in LLMs reasoning abilities under format restrictions" and "stricter format constraints generally lead to greater performance degradation" (https://arxiv.org/abs/2408.02442). StructuredRAG: Gemini 1.5 Pro and 4-bit Llama 3 8B average 82.55% success but "ranging from 0 to 100%", lists and composite objects hardest (https://arxiv.org/abs/2408.11061). Galeone et al. (May 2026), 7–9B models: naive prompting "up to 85% task accuracy" yet 0% usable JSON; constrained decoding "adds 3.6x to 8.2x latency" and can degrade the task (https://arxiv.org/abs/2605.02363). So: flat, small schemas for local models; judgement calls to a strong model.

**Prompt shape.** The evidence favours two-pass extract-then-normalise with per-chunk extraction: entities, then relations conditioned on the entity list (KGGen); ~600-token chunks or a gleaning loop (GraphRAG); LLM-free alias aggregation; embedding-blocked LLM arbitration (KGGen). No source shows per-sentence tagging beating per-chunk tuples for KG building; per-sentence tagging is what GLiNER-style encoders do cheaply.

## 2. Entity linking to Wikidata/Wikipedia

**wbsearchentities** "Searches for entities using labels and aliases"; `limit` max 50, default 7; `strictlanguage` disables fallback (https://www.wikidata.org/w/api.php?action=help&modules=wbsearchentities). Strait of Hormuz is Q79883: P31 strait, P625 26°36'N 56°30'E, GeoNames 287878, width 55 km, basin countries Iran/Oman/UAE (https://www.wikidata.org/wiki/Q79883).

**Etiquette.** "There is no hard speed limit on read requests, but be considerate and try not to take a site down"; requests "in series rather than in parallel"; batch with `|`; `Accept-Encoding: gzip`; `maxlag` for non-interactive jobs; descriptive User-Agent; exponential backoff on `ratelimited` (https://www.mediawiki.org/wiki/API:Etiquette). Access policy: User-Agent `<client name>/<version> (<contact information>) <library/framework name>/<version>`; clients without one "may be blocked without notice"; "Authenticated API requests receive higher rate limits" (https://www.mediawiki.org/wiki/Wikimedia_APIs/Access_policy). The numeric rate-limit page redirected and I could not read it; a Phabricator thread cites 50 req/s from old config, unverified. Treat the number as unknown.

**Reconciliation API.** W3C Entity Reconciliation CG spec v0.2 (10 Apr 2023): manifest endpoint, batched `queries` POSTed as JSON (`query`, `type`, `limit`, `properties`, `type_strict`), candidates with `id`, `name`, `score`, `match`, optional suggest endpoints (https://www.w3.org/community/reports/reconciliation/CG-FINAL-specs-0.2-20230410/). The Wikidata service is at `https://wikidata-reconciliation.wmcloud.org/en/api` (swap `en`); strings fuzzy-matched, identifiers exact, coordinates score 100 when equal and 0 at 1 km apart; no rate limit stated (https://wikidata-reconciliation.wmcloud.org/). OpenRefine's type filter "will include that type and all of its subtypes" (https://openrefine.org/docs/manual/wikibase/reconciling). Plain JSON over HTTP, property-constrained: the most Node-friendly linker there is.

**Neural linkers.** REL: Python + web API, English Wikipedia 2014/2019, Flair NER; mention detection 2.41 s/doc on CPU vs 0.44 s on GPU (https://github.com/informagi/REL). BLINK: bi-encoder then cross-encoder over a 2019-08-01 dump, "fast mode" bi-encoder only (https://github.com/facebookresearch/BLINK). GENRE/mGENRE: constrained beam search over a title trie, BART/mBART on fairseq ("changing without backward compatibility"), sizes unstated (https://github.com/facebookresearch/GENRE). OpenTapioca: "simple and fast" Wikidata linker, Apache-2.0, "kept synchronous with Wikidata in real time", public instance seeking funding (https://github.com/opentapioca/opentapioca). spaCy EntityLinker starts from "an empty knowledge base" you build, candidates from "exact, case-dependent aliases" plus priors (https://spacy.io/api/entitylinker). All Python, dated snapshots, GPU-leaning: poor fit for current news from Node.

**Practical approach.** No fetched source describes the full "label+alias+description → embeddings → LLM arbitration" recipe, but each part is documented: reconciliation/wbsearchentities give typed candidates with descriptions; KGGen shows BM25+embedding retrieval feeding an LLM duplicate judge. I guessed that composing them is the right Node design; it is consistent with every source but not itself sourced.

## 3. Deduplication across sources

**Embeddings.** nomic-embed-text-v1.5: Apache-2.0, 768-d with Matryoshka truncation (MTEB 62.28 at 768, 61.04 at 256), 8192 context, and a required task prefix: `clustering` is the one for "removing near-duplicates", not `search_*` (https://huggingface.co/nomic-ai/nomic-embed-text-v1.5). bge and text-embedding-3 not fetched.

**Record linkage.** Splink implements Fellegi–Sunter: match weight from m ("largely a measure of data quality") and u ("a measure of coincidence") (https://moj-analytical-services.github.io/splink/topic_guides/theory/fellegi_sunter.html). Threshold guidance is a procedure, not a number: pick recall vs precision, use the Threshold Selection Tool (needs labels), then "look at records on either side of your threshold to check whether the threshold makes intuitive sense", iterate (https://moj-analytical-services.github.io/splink/topic_guides/evaluation/edge_overview.html). dedupe: 1,000 records give 499,500 pairs, "it would take six days" at 1 s each, hence predicate blocking (https://docs.dedupe.io/en/latest/how-it-works/Making-smart-comparisons.html); threshold from expected precision/recall on a sample since "There's always a trade-off between precision and recall" (https://docs.dedupe.io/en/latest/how-it-works/Choosing-a-good-threshold.html). Zingg: Spark, active learning on "frugally small training samples", compares "0.05-1% of the possible problem space", AGPL v3 (https://github.com/zinggAI/zingg). All Python/JVM; in Node implement blocking + scoring yourself (the maths is small) and keep Splink's evaluation habit.

**Same name, different entity.** GDELT's codebook: `Geo_Fullname` "reflects differences in transliteration, alternative spellings, and alternative names", collapse on `Geo_FeatureID`; the organisation engine is "tuned to err on the side of inclusion", so "histogram the results and discard names appearing only once or twice" (http://data.gdeltproject.org/documentation/GDELT-Global_Knowledge_Graph_Codebook-V2.1.pdf). KGGen admits over/under-dedup; Neo4j warns of wrong merges. Nobody publishes a universal threshold; all say calibrate on your own labelled pairs.

## 4. Temporal and geospatial knowledge graphs

**Wikidata time.** Timestamp + precision code (9 year, 10 month, 11 day; nothing finer stored) + calendar model (Gregorian from 1583, Julian before). P585 point in time is "for describing point of time some statement was true"; P580/P582 "for describing period of time some statement was true" (https://www.wikidata.org/wiki/Help:Dates). Entity-state-at-t is qualified statements, not snapshots.

**GDELT.** GKG 2.1 (Leetaru, 2015): one row per document every 15 minutes; V2ENHANCED persons/organisations/locations/themes with character offsets; tone −100..+100 ("common values range between -10 and +10"); GCAM "more than 2,300 emotions and themes"; 65-language MT; date mentions. Entities are raw strings except locations, geocoded to GNS/GNIS FeatureIDs with a resolution type and centroid. Self-stated weaknesses: location extraction runs "in a more aggressive stance" with "a slightly elevated level of false positives"; organisations err toward inclusion; GKG 2.1 no longer clusters duplicate articles (GKG codebook above). Event codebook: dyadic CAMEO Actor1→Actor2, three-level EventCode, QuadClass, GoldsteinScale per event type ("two riots, one with 10 people and one with 10,000, will both receive the same Goldstein score"), NumMentions/AvgTone counted only "during the 15 minute update in which it was first seen", actor attributes "NOT supplemented from information in the text", separate georeferencing of actors and action (http://data.gdeltproject.org/documentation/GDELT-Event_Codebook-V2.0.pdf). The 2014 critique found only 39% of events with both actors, US/UK source bias; "machine coding is worse than human coding in terms of accuracy, but not terribly so" (https://politicalviolenceataglance.org/2014/02/20/raining-on-the-parade-some-cautions-regarding-the-global-database-of-events-language-and-tone-dataset/). Right: provenance, offsets, feature-ID geocoding, mentions separate from events. Wrong: dictionary-bound actors, string entities, no cross-document resolution.

**ICEWS** (Boschee et al., Leidos): CAMEO source/event/target triples "extracted from news articles by the BBN ACCENT event coder"; research/education only; "DISCONTINUED ON 11 APRIL 2023", successor POLECAT (https://dataverse.harvard.edu/api/datasets/export?exporter=dataverse_json&persistentId=doi:10.7910/DVN/28075).

**TKG literature.** Cai et al. (arXiv 2403.04782) survey graphs that "incorporate time information into the standard knowledge graph framework", benchmarked on ICEWS, GDELT, Wikidata, YAGO (https://arxiv.org/abs/2403.04782; dataset names from the search summary). It is link prediction over quadruples, not extraction; later use.

**EventKG** (Gottschalk & Demidova, SWJ 2019): RDF from Wikidata, DBpedia, YAGO and the Wikipedia Current Events Portal, `sem:hasBeginTimeStamp`/`sem:hasEndTimeStamp`/`sem:hasPlace`, 1.3M events, 4.5M temporal relations (https://eventkg.l3s.uni-hannover.de/). A sensible target vocabulary for event nodes.

**Bitemporal.** Fowler: "actual history records what history should be given perfect transmission of information"; "record history captures how our knowledge of history changes" (valid vs transaction time); needed because "Retroactive changes are a problem when actions are based on a past state that's retroactively changed" (https://martinfowler.com/articles/bitemporal-history.html). For news: valid time = when the fact held; transaction time = when source s published and when we ingested. "Entity sampled at t by source s" is then an observation row (entity, property, value, valid_from/to, source, published_at, ingested_at, extractor_version), never overwritten; the canonical view is computed over conflicting observations, as GDELT's Mentions relate to Events.

## 5. Gazetteers and geocoding

- **GeoNames**: CC BY, "give credit to GeoNames"; 10,000 credits/day, "the hourly limit is 1000 credits" per username (https://www.geonames.org/export/); `username` "required on every request" (https://www.geonames.org/export/web-services.html); search has `q`/`name`/`name_equals`, `featureClass`/`featureCode`, `fuzzy` 0–1, `maxRows` ≤1000, `inclBbox=true` for a bounding box (https://www.geonames.org/export/geonames-search.html). STRT is "a relatively narrow waterway … connecting two larger bodies of water"; also SEA, GULF, BAY, CHN, STM (https://www.geonames.org/export/codes.html).
- **Nominatim**: "an absolute maximum of 1 request per second", single thread, one machine, recurring scripts "restricted to 4 requests per minute", real User-Agent, "Results must be cached on your side", attribution (https://operations.osmfoundation.org/policies/nominatim/). Not for a pipeline.
- **Who's On First**: per-source licences (CC BY, CC0, OGL, MPL), link back required (https://whosonfirst.org/docs/licenses/); placetypes include `marinearea` and `ocean` (https://github.com/whosonfirst/whosonfirst-placetypes), so a strait can be a polygon record.
- **Natural Earth**: "in the public domain", "No permission is needed" (https://www.naturalearthdata.com/about/terms-of-use/); 10m physical labels have area polygons and label points, plus a marine-areas file (https://www.naturalearthdata.com/downloads/10m-physical-vectors/10m-physical-labels/).
- **Wikidata P625** is one WGS84 point (https://www.wikidata.org/wiki/Property:P625); Hormuz has point + width, no area.

**Point+radius vs polygon.** Three tiers from the sources: centroid (always), bbox (GeoNames `inclBbox`, Wikidata width), polygon (Natural Earth marine areas, WOF `marinearea`). I guessed the store shape: every place gets point + radius (from bbox diagonal or a per-feature-code default) and an optional polygon reference; the reconciliation service's 1 km coordinate scoring shows point matching alone is too strict for large features.

## 6. Sentiment, stance, POS at scale

compromise: "~250kb (minified)", MIT, "~1mb of text a second", `.people()/.places()/.organizations()`, no numeric accuracy claim (https://github.com/spencermountain/compromise). wink-nlp: MIT, "~10Kb" core, ~1 MB models, "over 650,000 tokens/second", POS "~95%" on a WSJ subset, sentiment f-score "~84.5%" on Amazon reviews, self-reported (https://github.com/winkjs/wink-nlp). GLiNER2 zero-shot classification averages 0.72 vs GPT-4o 0.84 (SST-2 0.86 vs 0.94) (https://arxiv.org/html/2507.18546v1). GDELT calls its tone "a basic tonal assessment" and points users to GCAM (Event codebook). No fetched source compares LLM stance labelling with classical tools on news; the format-restriction papers show small models lose accuracy on complex JSON, lists and composites worst (https://arxiv.org/abs/2408.11061). Verdict, partly guessed: classical POS buys nothing the LLM pass lacks; use wink-nlp for sentence splitting and a document-level sentiment sanity check; have the LLM emit per-relationship stance as a small enum.

## Recommendations for a small Node team

1. **Two phases, separate tables.** Phase A (pre-analysis, per document, cached and versioned by prompt+model): ~600-token chunks or a gleaning loop; entities first, then relations conditioned on the entity list; `mentions` with character offsets, like GDELT's V2ENHANCED fields; document publish time and source attached. Phase B (resolution, batch): LLM-free alias aggregation; nomic `clustering:` embeddings; block by (type, cluster, BM25 neighbours k≈16); LLM judge "exact duplicates only" per block; reconcile canonical names via the Reconciliation API with type/property constraints, `wbsearchentities` fallback. Mention→entity links are scored, revisable edges; never destructive merges.
2. **Schemas.** Flat, small JSON per call; enums for type and stance; verbatim spans for names. Ollama `format` at temperature 0 locally; Anthropic `output_config.format`/`strict` tools for arbitration; validate values yourself. Keep a labelled pair set and inspect both sides of every threshold, Splink-style.
3. **Libraries.** Node: wink-nlp, your own blocking + Fellegi–Sunter scoring, a Reconciliation API client, GeoNames client with bbox. Python sidecars only if GLiNER2/NuExtract beat ollama on the bulk NER pass. Skip REL/BLINK/GENRE.
4. **Etiquette.** One serial stream per upstream, descriptive User-Agent with contact, gzip, `maxlag` on Wikidata, cache every lookup, GeoNames under 1000/hour, Nominatim ≤1/s and never bulk.
5. **Store.** Bitemporal observations with source and extractor version; canonical view computed, not stored; SEM-style events with begin/end/place; places as point+radius plus optional polygon and GeoNames/Wikidata IDs.
6. **Failure modes.** Early-chunk recall loss; over/under-merging (homonyms, transliteration); ungrounded entities and relations (demand verbatim spans); schema drift across model versions (pin and version outputs); small-model JSON failures on lists; aggressive location false positives; source bias and duplicate reporting inflating counts; point-only matching for large features; upstream churn (the reconciliation host already moved from wikidata.reconci.link to wmcloud.org).

Unverified: bge/text-embedding-3 cards, Wikimedia's numeric rate limits, iText2KG's resolution internals, mGENRE sizes, GLiNER2 relation quality, any news-specific hallucination rate for LLM triple extraction.
